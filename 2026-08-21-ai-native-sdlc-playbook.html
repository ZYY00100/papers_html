01
INTRO · BOTTLENECK

Code Is No Longer the Bottleneck

代码不再是瓶颈
CORE THESIS Organizations have started using AI to write code at a speed unthinkable one year ago, yet the processes around the code haven't changed at the same pace.

很多团队已经开始用 AI 以一年前不可思议的速度写代码,然而围绕代码的那些流程——审批 gate、review、handoff、policy——并没有以同样的速度变化。

很多工程团队还保留着同样的审批 gate、review、handoff 和 policy,这些流程正在拖住 agentic coding 工具(如 Claude Code)带来的生产力提升。

SDLC(software development lifecycle),是从一个想法走到 production 软件的完整流程。大多数组织跑的版本都覆盖六个 stage——planning、design、building、testing、deploying、maintaining。传统上,每个 stage 都是一个由不同角色拥有的离散阶段:product manager 写需求、technical architect 转成 design、engineer 实现、QA 团队 verify、release team 上线、operations 监控运行。Work 通过 documents、tickets、sign-offs 在这些阶段之间流动。

传统 SDLC 流程重,目的是保证每个步骤的 accountability 和 control。但传统 SDLC 是为"最耗时最贵的阶段是写代码"那个时代设计的——而那个时代已经过去了。PRD、estimation ritual、product security review 这些流程之所以存在,是因为开发工作可能要数周、数月、甚至数季,需要 force alignment。

传统 SDLC 还假设每一步都是人做的。价值产出最多的那些组织已经围绕"agentic AI 现在能做什么"重建了他们的流程,同时确保 human 留在 loop 里。本 guide 走一遍我们 Applied AI 团队内部整合 Claude 的最佳实践,基于我们与客户合作的经验,逐 stage 加速开发、让流程跑得更快。

当代码不再是瓶颈、build phase 比传统 SDLC 允许的还快时,有三件事变成真的:

  • 瓶颈移到 build phase 左和右的 stage——主要是 plan、review/test、deploy,它们仍然以 human speed 在跑。
  • Controls 跟不上 reality,变成 intractable。每行代码都人工 review,在人写的代码时代是合理的;一旦 agent 写了大部分 diff,review 就跟不上了。
  • Governance 成本上升——exception 仍然通过 meeting 和 committee 走,那些 meeting 每周或每月才开一次。

以 security bottleneck 为例:security team 的 size 是按人输出算的,当 agent 放大代码输出时,review queue 要么堆积,要么代码在 under-reviewed 状态下被 ship 出去。受监管的组织不能接受这两种结果——所以它的 security 和 policy check 必须跟上 agent 的速度。

为了更好地释放 agentic AI 的生产力,同时保证安全,传统 SDLC lifecycle 需要跟 implementation phase 经历过的那场同等规模的转型。

02
DEFINITION

What Is an AI-Native SDLC?

什么是 AI-Native SDLC
CORE PRINCIPLE AI-Native SDLC 是一套重新设计过的 process——把旧的控制目标和新的 enforcement 机制结合起来。流程不再是 linear flow,而是一个 loop,AI 嵌入在每个节点上。

AI-Native SDLC 是一套重新设计过的 process——把旧的控制目标和新的 enforcement 机制结合起来。流程不再是 linear flow,而是一个 loop,AI 嵌入在每个节点上。AI-Native SDLC 主张自动化的 handover 和下一阶段的自动触发,缓解传统 SDLC 阶段之间那种手动、僵的交接。

你也可能听到这个转变被叫作 agentic SDLC、AI SDLC,或者直接叫 agentic software development——名字不同,说的都是同一件事。

六个 stage 的两端

下表展示传统 SDLC 和 Claude 支撑的 AI-Native SDLC 之间的 spectrum 两端。大多数组织会落在两列之间的某个位置。

StageTraditional SDLCAI-Native SDLC
Plan Requirements gathered by committee, distilled through workshops and sign-offs, written up by hand. 由 committee 通过 workshop 和签字流程手工收集需求、写下来;通过 Claude 直接从 source 中综合 pain points,把它们写入 intent.md——人可读、机器可执行。
Design Spec written by analysts, parsed by designers. 需求和设计压缩成一次 working session,由 agent 主导;由编码为 skills 的标准引导,在 git 里版本管理。
Build Tests and code are handwritten and documentation is written after the main development happens. 测试和代码由 AI 生成,机构知识以版本化的、机器可读的 CLAUDE.md 和 skills 形式持续维护。
Test QA gates at stage boundaries. QA gate 设在 stage 边界。Continuous evals 嵌入到整个 implementation 流程里。
Deploy Humans review every line of code and governance occurs in review cycles, often inconsistently. 多层 agentic review,人工 review 只留给受监管和关键代码。Governance 在 AI 行动时被强制执行——hooks 作为审批 gate。
Maintain Humans watch production for bugs. Agents 监控线上部署。任何 control band 被突破,都会被自动诊断并写回 loop 里,成为下一份 intent.md。

贯穿右列的那条线,是 committed artifact。每个 stage 结束都把一个 artifact 写入 version control(intent.md、spec.md、plan.md、diff 及其测试、带 review findings 的 PR、incident record),下一个 stage 开始时读它。前几个 stage 以 .md 文件为主,因为 product owner 和 agent 能读、能操作同一份文件。从 Build 开始,artifact 是 code 及其记录。commit 链同时也是 audit trail:谁要了什么、agent 产出了什么、谁批准的。

每个需要判断力的决定,人仍然 accountable。在 agentic SDLC 的世界里,human attention 跟着那些必须被 review 的 artifact 一起移动。

每个 stage 都 commit 一个下一个 stage 能读的 artifact。Intent、spec、plan、diff、review findings 加在一起,就是 audit trail。

OVERVIEW

Plays · The Six Stages & Their Dependencies

Plays · 六个 stage 与它们的依赖关系
CORE PRINCIPLE Plays 是 playbook 的核心,分成 6 个非线性 stage(Plan / Design / Build / Test / Deploy / Maintain),共同覆盖整个 lifecycle。每个 stage 结束都 commit 一个 artifact,下一个 stage 由它触发。

Plays 是 playbook 的核心,分成 6 个非线性 stage(Plan、Design、Build、Test、Deploy、Maintain),共同覆盖完整的 lifecycle。

    每个 play 覆盖:

    • 改了什么;
    • 如何开始;
    • 具体的实施步骤;
    • Governance 注意事项;
    • 如何衡量是否有效。

    这些步骤是模块化的,组织可以基于各自需求,优先选择不同 stage 来转型。每个 play 都在 "Prerequisites" 下注明依赖项,dependency graph 进一步展示了依赖关系。

    一个 stage 的结束是 commit 一个 artifact,而该 commit 触发下一个 stage。被接受的 intent.md 触发需求和 design pass、被批准的 spec.md 触发 plan mode、被合并的 PR 触发 pipeline,生产中突破的 control band 写出下一份 intent.md——loop 就这样转下去。

    首先,手动逐个 step 进行 prompt,目标态是一个 loop——每个被接受的 artifact 触发下一个 gate。Human attention 集中在 gate,review agent 标记的内容,而不是每次从零开始启动一个 stage。

    原文配图 · Plays 列在 stage 下;箭头指示的是采用顺序。两者不是一回事。从任何"clay play"(没有箭头指向它的 play)开始——它不需要先做什么。对于其他 play,指向它的箭头就是先要采用的 play。

04
STAGE 1 · PLAN

Plan · Capture as intent.md

Plan:用 intent.md 把意图锁定下来
CORE PRINCIPLE Ideas stop waiting for someone to write them up. Intent is captured once, in the originator's own words, as a version-controlled artifact the next stage can act on.

Traditional vs AI-native

传统 · 一个想法要经过 backlog entries、user stories、story points、refinement meetings 才能有人动它。所有权在每次 handoff 时转移,等它到达 engineering 那里时,已经跟提出者原意隔了好几手。

AI-Native · 提出者跟 Claude brainstorm,把结果写成 intent.md——一份用提出者自己语言写的 proto-spec。Artifact 包含"要什么"、"为什么"、"在什么约束下"。重复流程通过 skills 编码。

Getting started

Prerequisites · 无。

Infrastructure · 给非工程师开放 Claude 访问(claude.ai 或 Cowork);一份商定的 intent.md 模板;product owner 盯着的一个共享、版本化的 intent 存储位置。对单一产品来说,最简单就是产品 repo 里的 intent/ 目录——artifact 链和由它派生出来的 code 放在一起。Intent 跨很多 repo 时才值得开一个独立 intent repo,monorepo 的话直接是目录。Stage 3: Build 的侧栏会讲这个 home 跟现有 Jira 或 requirements 工具怎么衔接。

这件事由 platform 或 engineering team 一次性完成。需要一名技术团队成员搭起 intent home,决定谁能写——因为很多贡献者会来自整个组织。

Repository 搭好之后,没有 git 经验的贡献者也不用直接用 git。VCS(比如 GitHub)的 connector 让 Claude 从 claude.ai 或 Cowork 代为 commit markdown 文件。

How to execute it

    1. 提出者用自己语言把问题描述给 Claude。可以描述今天做不了什么、谁被这个想法影响、better 长什么样、什么 out of scope。不需要正式语言。
    2. 一起 brainstorm,直到想法具体化。Claude 会问 analyst 通常会问的那些问题:scope、users、constraints、成功的样子。
    3. 让 Claude 用组织模板把结果写成 intent.md。模板可以由技术团队成员编码为 skill,由 lead 签发。可以覆盖 problem、proposed outcome、affected users and systems、constraints、open questions。
    4. 提出者纠正 Claude 误解的地方。
    5. 把 intent.md commit 到共享 home。作者和时间戳一起进入记录,product owner 从那里接下这个想法。

    模板示例:

    .md
    intent.md 意图文档 · 模板
    PLAN · GOVERNANCE
    # Intent: claims status self-service Author: J. Ortiz (claims operations). Status: draft. ## Problem Customers phone the contact center to ask where their claim is. Handlers spend roughly a third of call time on status-only queries. ## Proposed outcome Customers see claim status, next step and expected date in the portal. ## Affected users and systems Claims handlers, portal team, claims-core API. ## Constraints No new PII in the portal session. Existing authentication only. ## Open questions Do third-party loss adjusters need access too?
    # 意图:理赔状态自助查询 作者:J. Ortiz(理赔运营)。 状态:草稿。 ## 问题 客户打电话到联络中心,问他们的理赔在哪一步。坐席大约有三分之一的通话时间花在了"只查状态"这类查询上。 ## 期望结果 客户在门户里就能看到理赔状态、下一步动作和预计完成日期。 ## 受影响的用户和系统 理赔坐席、门户团队、claims-core API。 ## 约束 门户会话中不能再引入新的 PII。只用现有认证。 ## 尚未回答 第三方定损员是否也需要访问?

    Governance considerations

    证据就是那份被 commit 的 intent.md,其中包含作者、时间戳、完整的 revision history。它记在 intent home 的 git 历史中。Product owner 批准,然后把 intent 送到 Stage 2: Design 的"接受/拒绝"决定,以合并或关闭 review 的形式记录下来。

    How to measure it

    领先指标 · 从第一次对话到一份被 commit 的 intent.md 所用的时间,直接从 intent home 的 git history 读取,那里有作者和时间戳。期望从原来多周的 elicit 和 refinement cycle 降到小时级。

    滞后指标 · "存活率",也就是 product owner 接受进入 Stage 2: Design、而不是关闭的 intent.md 占比。接受/拒绝决定以合并 artifact 或关闭 review 记录。同一个 change 在首次 spec.md commit 之后还改了 intent.md 的次数。

05
STAGE 2 · DESIGN

Design · Requirements & Design

Design:需求与设计一步到位
CORE PRINCIPLE Requirements and design collapse into one session. Policy is applied while the spec is written, not discovered in a review weeks later.

Traditional vs AI-native

传统 · 需求和设计是 separate phases,由 separate teams 跑。Analyst 把想法变成 requirements,designer 再把它 parse 回 design。分开是因为 accountability,但慢、且有信息损失。

AI-Native · 两个 phase 在同一个 prompted session 里发生。Claude 读 intent.md,产出 requirements 和 design spec,被组织的 skills 约束,concerned 区域会被标出。

Getting started

Prerequisites · 先写一份 intent.md 文件,brand / security / compliance / UX 政策以 skills 形式存在。

Infrastructure · 一名有 Claude 访问权限的 product owner。不需要工程技能。

How to execute it

    1. Product owner 开一个 session,加载组织 skills,attach 上 intent.md。
    2. Product owner 的 prompt 指向 intent.md,点明约束,要求标出 concerns。先手动跑,再编码成组织级 slash command。之后把 intent.md 在 intent home 里被接受作为触发,跑一个 non-interactive job 在 merge 时触发,加载组织 skills 跑这次 pass,把 spec.md commit 成 PR(Stage 5: Deploy 的 CI/CD play 负责管 plumbing)。从那开始,product owner 第一次主动介入是 review。
    3. 同一位 product owner 把 spec 对照 idea 一起 review。Spec 是否解决了 stated problem?intent.md 里的 open questions 是被回答了,还是被 carry forward 了?
    4. 先处理 flagged concerns——它们是 analyst 通常会 escalate 的点。Product owner 在 engineering 看到 spec 之前,先和对应的 policy owner 把每一项解决。
    5. 把 spec.md 跟 intent.md 一起 commit。文件 pair 记录了"要了什么"、"决定了什么"。
    6. Product owner 决定 spec 和 intent 是否进入 build,任何组织划为高风险的项都要咨询 technical lead。这件事一定由人做决定,接受 spec 就是启动 Stage 3: Build 的 plan mode play。

    What it looks like (the prompt)

    .md
    spec.md prompt 需求与设计 prompt
    DESIGN · GOVERNANCE
    Read the attached intent.md and produce a requirements and design spec for integrating it into our existing codebase. Apply the skills available to you so the plan conforms to our brand guidelines, security policies and UX standards. Document the spec fully as spec.md, ready to hand to the engineering team. Describe clearly any areas of concern, especially where you cannot satisfy contradicting policies.
    读取附件里的 intent.md,为把它集成进我们现有 codebase,产出 requirements 与 design spec。应用你可以拿到的 skills,使计划符合我们的 brand 指南、安全政策和 UX 标准。把 spec 完整写进 spec.md,准备好交给 engineering team。清楚描述任何 concerns,尤其是当你无法同时满足相互冲突的 policy 时。

    Governance considerations

    Live policy 在 spec 被写的时候就读出来应用,不是在几周后的 review 才发现。组织的 skills 作为 spec 的 constraints 落地。Spec、生成它的 prompt、当时生效的 skill 版本,全部记在 version control 里。Product owner 给 spec 签字,再把 flagged concerns 转给指定的 policy owner。

    How to measure it

    领先指标 · 同同一个 change 的 intent.md commit 与 spec.md commit 之间的时间差(两个 git timestamp),与过去 requirements+design cycle 的对比。

    滞后指标 · Build 启动后的 requirements rework 数。统计同同一个 change 在首次 plan.md commit 之后还 commit spec.md 的次数。Git log 直接给出。

STAGE 3 · BUILD

Build · Plan Mode · CLAUDE.md · Skills · Hooks

Build:Plan mode / CLAUDE.md / Skills / Hooks
CORE PRINCIPLE Nothing is implemented without an accepted plan. Institutional knowledge becomes files the agent reads, and the guardrails run as code rather than as habits.

Claude Code plan mode as the default starting point

传统 · Engineer 读 design 然后开始写代码。怎么改、改哪些文件、哪些测试,都在 engineer 脑子里,或者顶多写在 ticket comment。其他人无法 review。Reviewer 看到的第一眼是已经写好的 diff,等发现 rework 已经慢了。

AI-Native · 工作从一份书面 plan 开始。Claude 在 plan mode 里产出 plan,只能读 codebase,不能改任何东西。Engineer 在代码被写之前先纠正 plan,通过的版本作为 plan.md commit,供后续 stage 对照。

Prerequisites · intent artifact(intent.md 或 spec.md),如果有的话;还有 CLAUDE.md 文件会很有帮助。

Infrastructure · Claude Code,可以访问 repository。

    .md
    plan.md 实施计划模板
    BUILD · GOVERNANCE
    # Plan: claims status self-service (from intent.md 2026-06-02) ## Files that change portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py, claims-api/tests/test_status.py ## Order of work 1. Add the status endpoint behind existing auth. 2. Panel against the endpoint. 3. Wire into the portal nav. ## Risks The claims-core API rate-limits at 50 rps; the panel must cache. ## Proof test_status.py covers the four claim states; screenshot matches the approved mock.
    # 实施计划:理赔状态自助查询(基于 intent.md 2026-06-02) ## 改动的文件 portal/src/claims/StatusPanel.tsx(新增)、claims-api/routes/status.py、claims-api/tests/test_status.py ## 工作顺序 1. 在现有 auth 后面加 status 端点。 2. 把 panel 接到端点上。 3. 接入门户导航。 ## 风险 claims-core API 限流到 50 rps;panel 必须缓存。 ## 验证标准 test_status.py 覆盖 4 种 claim 状态;截图与已批准的 mock 一致。

    Governance considerations · Design review 发生在任何代码被生成之前——那时改方向还只是改一份文档。Plan mode 本身就强制了这一点,因为 Claude 在 engineer 接受 plan 之前不能编辑文件。Plan 和它的 revision 与"谁接受的"一起被记录。Routine changes 由 engineer 批准,任何组织划为高风险的项交给 tech lead 或 architect。

    How to measure it · 领先:第一次 implementation pass 就合并的 change 占比,以及从 plan approve 到 PR 合入的时间(从 PR metadata 取)。滞后:每个 change 的 rework cycle 数(同样从 PR metadata 取),以及合并后的 diff 与 plan.md 还匹配的频率。

    Claude Code on auto-mode

    Claude Code 还能以 auto-mode 跑——engineer 批准 plan,满意并迭代过之后,Claude 直接 apply 每一处改动,不再每个 edit 都 prompt 一次。随着后面 play 的 guardrails 成熟(调好的 CLAUDE.md、编码了 policy 的 skills、挡住不安全 action 的 hooks、以及 Claude 能跑的测试套件),auto-accept 就成了 routine work 的默认:一份紧凑的 spec.md、小 blast radius、代码在测试已经覆盖的范围里。

    重点现在从"用户盯着 agent 改东西、review 它每一个 action",转向"在更长的自主 session 之后,review artifact"。Auto-accept 模式配合 worktrees,还能让个人与团队之间并行起来,是让 SDLC 自主跑、闭环起来的基础(见 Stage 6: Maintenance)。

    SIDEBAR · LEGACY SYSTEMS & SOURCE OF TRUTH

    适用于这个流程产生的每一个 artifact。

    现有 SDLC 流程很可能已经在跟踪 artifact,只是不在 markdown 文件里。Work items 可能在 Jira,requirements 在带合规追溯的工具里,design 在 Figma,变更审批有 change board。这些系统很难替换,因为 auditor 和 regulator 已经接受它们,其他团队也依赖它们,所以 AI-Native SDLC 必须围绕现有体系来设计。

    过渡到 AI-Native SDLC 时,对流程产出的每个 artifact,指定一个 system 作为 source of truth,其他系统持有副本或到原版的链接。下面这些配置可以做到"一个 source of truth",每个 artifact 各自选哪个:

    Repo 作为 source of truth。 Markdown artifact 是 authoritative record,legacy system 只引用 commit 里的文件。对工程主导的组织来说,这通常是最干净的——所有记录都活在同一个工具、同一套 timestamp 权威下。

    Legacy system 作为 source of truth。 Jira、ServiceNow 或 requirements 工具持 authoritative record,markdown artifact 是 working copies。Claude 在 session 开始时读记录,在产出 spec 或 plan 的同一个 session 里,通过 MCP connector 把结果写回去。

    Linkage 是最低底线。 所有 artifact 记录 record ID,所有 legacy 记录包含 markdown 文件的 commit SHA。过渡到 AI-Native SDLC 时,从 linkage 开始是个稳妥起点,接受两个 source of truth 存在的事实。

    Legacy system 和 markdown-first system 可以共存,只要两者之间有 link,或其中一方被明确为 source of truth。

      Skills as institutional knowledge

      Skills 是一个组织让机构知识变得可执行的方式。指令显式、版本化、广泛适用,policy 变化时统一更新。经验法则:为"必须一致应用"的机构知识写 skill;不要为那些应该放在 CLAUDE.md 或 prompt 里的组件写 skill。

        How to measure it · 领先:从 policy owner 批准 policy 修改到更新后的 skill 合入的时间,从 skill 文件夹的 PR 取。滞后:PR review 中引用该 policy 的 findings 数,在 skill 在写代码时就应用 policy 之后应该趋近于零。如果没趋近于零,要么是 skill 没触发,要么是它的文字已经跟官方 policy 漂移了。

        Hooks as build-time guardrails

        Skill 是 advisory control,hook 是它身后的 deterministic layer。Claude 在 implementation 期间的绝大多数 action 都是 file edit 和 shell command,所以 build phase 是 hook 触发最频繁的地方。

          Build-phase hook 可以:

          • 阻挡针对受保护路径的 edit,比如 generated class 或冻结的 package;
          • file edit 之后跑 formatter 和 linter,让 drift 不积累;
          • 让 credentials 不出现在 diff 里。

          凡是不允许例外的 policy 都要靠 hook 兜。Hook 对每个匹配的 action 都会跑一次,所以 build-phase 的 hook 要快、范围只覆盖改动过的文件。更重的检查,比如完整测试套件,放到 commit 或 PR 那一步。

          那种"问人批不批"的 hook,跟 Stage 5: Deploy 里的 gate 是一类——build 中弹审批 prompt,等于把所有并行 session 的 critical path 上又塞回一个人。

          Parallel sessions and subagents

          一名工程师可以同时推进多条 work stream。

          Parallel session 是另一个完整的 Claude Code 实例,在一个 git worktree 里跑独立 task。每个独立 session 之间互不知情,唯一共享的是在 steering 它们的工程师。

          Subagent 跑在单个 session 里,是一个 scoped helper,有自己的 context window 和 tool 限制,适合那些在多个 task 里反复出现的小活儿,比如"验证 app 能跑"。

          Parallel session 提高工程师可以同时 in-flight 的 task 数量,subagent 让每个 session 专注在自己的 task 上。Engineer 的工作变成 steering 和 review 它们。

          传统 · 一名工程师一次做一个 task,每天/每周的大量时间花在 build、test、review 上。等的时候可以换 task,但 context switch 太累,很少有人这么做。

          AI-Native · 一名工程师同时跑多个 Claude session,每个在自己的 worktree 跑自己的 task。重复的小活儿变成有自己 context 和 tool 限制的 subagent。Engineer 的工作转向 orchestration,最终转向构建和监控 loop。

          Prerequisites · CLAUDE.md,因为所有 session 都会读它。Feedback loop(Stage 4: Test)在这里也有用,session 能自己 verify 自己时,工程师就不需要那么多监督。

          Infrastructure · 一个 git repository,因为隔离来自 worktrees 和 permission 设置,后者被调成 session 不会为"组织认为安全"的命令等审批 prompt。

STAGE 4 · TEST

CORE PRINCIPLE Every session checks its own work before a human sees it, and the configuration that steers the agent gets regression-tested like the code it writes.

Give Claude a feedback loop

无论测试、build 还是截图 diff,永远给 Claude 一个能 verify 自己工作的方式。Session 在 engineer 看到之前先自己 check、自己修自己错的地方。

Feedback loop 不要和 verifier subagent(Stage 3: Build)混淆。Feedback loop 在整个 task 里,按工作的需要跑很多次。Verifier subagent 则是一种"打 final check 包"的方式——session 自认为工作做完了,用一个 fresh context window 跑一次。这样判断不会受"产出代码时的假设"所染。

传统 · 代码能 work 的信号来得很晚——CI 几分钟后、tester 几天后、生产几周后。当 agent 在产出代码时,信号晚到就意味着要人去检查全部产出,那个人就成了瓶颈。

AI-Native · Session 拿到一种方法,在人看到之前自己先 check。跑测试、跑 build、截屏。Claude 迭代到 check 通过,所以到 engineer 手里时已经通过了。Setup 这个 loop 是跑 session 的 engineer 的事,下面的步骤也是为他们写的。

Prerequisites · 无。

Infrastructure · 测试套件和 build,本地一条命令就能跑起来。做 UI 的话,让 Claude 能"看到"结果很关键——可以是一个浏览器工具,或通过 MCP 接进来的截图工具。

Continuous evals in CI

Evals 是 stage-gate QA 在 AI-Native 时代的等价物。实际就是一套 suite,在 agent 的 configuration 变化时跑。新 model 被换上、或 prompt 被重写时,eval suite 会告诉你 agent 是否还在按同样的 standard 干活。

Evals 应被当作活的 suite。Model 进步之后,以前能区分的 case 不再区分,就要靠持续 monitoring 来的新 case 补进去。

看 use case,有些团队可能愿意以固定节奏 offline 跑这些 evals,而不是每次 change 都跑。下面的步骤是为 continuous evals 写的。

Prerequisites · CLAUDE.md 和 feedback loop(Stage 4: Test)。

Infrastructure · CI 能以 non-interactive 方式跑 Claude Code,以及一个有 eval 预算的 API key。

AI in the PR review loop

Claude 既 review 也被 review。它按组织 policy review 进来的 PR,也处理它自己 PR 上的 review comments。这样工程师就能专注于"behavior"层面的 review——本质上是在判断 intent 和 risk。

      每一行在 control 维度上买到了什么

      permissions.deny 让 secrets 不进入 agent 的 context,也阻挡工具层的任意 network egress;permissions.allow 预批准安全的 inner loop,免得 deny list 变成 prompt fatigue。

      How to measure it(对 hook 本身) · 领先:每个 approval gate 上花掉的时间。每每条 hook 决定带 timestamp和 an allow or block verdict 记到 OpenTelemetry export,所以每个 gate 的等待都看得见。滞后:hook 启用前后,到达生产的 gate violations,从 incident tracker 取。

      CI/CD integration and deployment

      在 CI/CD pipeline 里以 non-interactive 方式跑 Claude Code,把执行 sandbox 起来让长跑的 agent 安全运行,把 deployment 通过 MCP integration 暴露出来,在 agent 需要回滚路径之前先演练一遍。

      传统 · Pipeline 跑 deterministic script,任何需要判断力的东西等一个人来。比如 triage flaky test、写 changelog、查 build 为什么挂了。Deployment 和 rollback 是人在压力下照着 runbook 操作。

      AI-Native · Claude 在 pipeline 里以 non-interactive 方式跑 judgment 步骤,在 sandbox 里,带着 scoped 凭证。Deployment 工具通过 MCP 暴露给 agent,所以同一套 workflow 既写也测也上线也回滚,被组织按环境定义的 gate 包着。

      Prerequisites · Claude in the PR review loop,以及 hooks as approval gates——因为自动化加速任何东西穿过 gate 之前,gate 必须先在。

      Infrastructure · 装了 claude-code-action 的 CI 平台,或能调用 claude -p 的 runner;流量必须留在组织云合约里的就走 API、Bedrock、Foundry 或 Vertex;为 deployment target 配 MCP server;agent job 用没有长期 production 凭证的 sandbox profile。

        YAML · PIPELINE STEP

        Governance considerations · 治理原则是:agent 可以在 production gate 之前做事,不能跨过它。下面这些 control 在强制这条原则。

        • Branch protection 把 agent 写的任何东西变成 PR,没有直接到 main 的路径。
        • Production deploy hook 挡住 release,直到具名 release manager 授权。每次 non-interactive 运行都在 agent 自己的 identity 下,所以 pipeline log 把"agent 做了什么"与"触发它的工程师做了什么"分开。
        • 按环境的 permission tier 决定 agent 在走到 gate 这一路上能做什么。

        How to measure it · 领先:不叫人、就被 triage 掉的 pipeline failure 占比,从 CI/CD pipeline log 取。滞后:DORA(DevOps Research and Assessment)指标——CI 体系和 deployment 工具本来就会 emit。

STAGE 6 · MAINTAIN

Maintain · Closing the Loop · Recurring Scans · Claude Tag

Maintain:闭环 / 周期扫描 / Claude Tag
CORE PRINCIPLE The loop closes. A trigger invokes Claude with no person in the invocation path, and what it finds re-enters the pipeline as intent.md.

Maintenance and closing the loop

到目前为止,我们讲的是怎么把 Claude 加到 SDLC 的每个 stage,每个阶段一开始还要人来启动。这一 stage 把焦点转向让 Claude 自主跑,让 loop 闭环。

例如,一个持续跑的 monitoring agent 可以在 bug ticket 一被开出来之后,立刻建一份 intent.md,然后流过 requirements、plan、build、test、review 等阶段。Stage 6: Maintenance 跑在 headless,每个阶段之间有一道独立的 confidence gate(deterministic check 或对抗式 reviewing agent)决定上一阶段的产出是继续走,还是 escalate 给一个人。

传统 · Maintenance 是被动阶段。所有 ticket 或 incident 都等一个人来动作、重启流程。凌晨 3 点 报警可能可能漏掉;一个 ticket 可能可能躺在 backlog 没人接;post-mortem action 可能根本进不了 codebase,如果另一场火先起。

AI-Native · 一个 trigger(control-band breach、ticket、channel message、schedule)在路径上无人,直接调起 Claude。Claude 诊断、只走 gated 路径做事、把发现写成 intent.md,然后顺着讲过的那些 stage 流下去。人来 triage 和 review 这些工作,但不再亲自启动它。

Closing the loop

一段 deterministic 脚本盯着 production,在 control band 被突破时调起 Claude。监控一个 breach 是 loop 自主跑的一个有用的例子,Claude Tag(public beta)那段讲的是通过不同 channel 进来的工作。

Prerequisites · intent.md——它给 loop 一个结构化的输出用来重启。加速过的 PR review、hooks as an action boundary、CI/CD 的 rollback path(最高自治 tier 会调起)。

Infrastructure · 检测脚本能查的 metrics store(Prometheus、CI 系统的 API 或等价的);repo 的读权限;在 CI 里 non-interactive 跑 Claude Code 的方法;接收 webhook 的服务用 Agent SDK。

    .yml
    bands.yaml 监控 bands 配置
    MAINTAIN · CONTROL BAND
    metric: ci_test_failure_rate baseline: rolling_30d rules: western_electric tiers: 1sigma: { action: log } 2sigma: { action: diagnose, tools: "Read,Grep,Bash(gh run view *)" } 3sigma: { action: propose, routes: [pull_request, runbook:rollback-deploy] }
    # 监控阈值配置(bands.yaml) > 这是一份控制带配置,用于决定 monitoring agent 何时该被调起、调起后能做什么。 ## 监控对象 - **指标**:CI 测试失败率(`ci_test_failure_rate`) - **基准线**:用过去 30 天(`rolling_30d`)的滚动窗口作为对照基线 - **判定规则**:Western Electric 规则——经典 SPC(统计过程控制)规则,既能抓住 spike 也能抓 slow drift ## 分级响应(tiers) 按偏离基准线几个 σ(标准差)分级: ### 1σ(1 个标准差以内,小波动) - **动作**:只记录到日志,不调起 Claude ### 2σ(2 个标准差,明显异常) - **动作**:调起 Claude 诊断(diagnose) - **允许使用的工具**:`Read` / `Grep` / `Bash(gh run view *)`——纯只读,不能改任何东西 ### 3σ(3 个标准差,严重突破) - **动作**:让 Claude 提议修复(propose) - **能走的两条路**: - 开一个 PR 到 review gate(让人 review 后再合并) - 触发事先批准过的 runbook:rollback-deploy(回滚部署的标准操作) ## 字段含义速查 - `metric` = 被监控的指标名 - `baseline` = 基准线算法 - `rules` = 判定规则 - `tiers.sigma` = 偏离 N 个标准差时的响应 - `action` = 这个 tier 触发时该做什么(`log` / `diagnose` / `propose` / 其他自定义) - `tools` = diagnose 阶段允许调用的工具白名单 - `routes` = propose 阶段允许走的修复路径白名单 YAML 字段是配置,英文原貌便于直接复制使用。

    Governance considerations · Tier 边界从 version-controlled config 强制,permission 和 managed settings deny 掉 production 访问。Invocation、finding、triage 决定都带 timestamp 记录。Service owner triage 和批准 finding,改动走正常 PR review gate,agent 可以触发的 runbook 都是事先批准过的。

    How to measure it · 领先:从 band breach 到 triage queue 里出现一份 intent.md 的耗时,对照过去从 incident 到 post-mortem action 的时间。检测脚本的 log 里有 breach timestamp 和 incident tier。滞后:变 merged fixes 的 finding 占比(triage queue 对照实际 PR history),以及同类的重复 incident 数——随着 fix 加进 eval suite,这个数应该下降。

      • 当 CI test failure rate 突破 3σ,agent 隔离 flaky test 或开一个 revert PR,review gate 决定。
      • 当 post-deploy 5xx rate 在窗口里有 deployment 时突破 3σ,agent 触发已有的 rollback pipeline。
      • 当 PR cycle time 触发 drift rule,agent 写一份报告给工程 leadership——harness 对过程 metrics 也跟对生产 metrics 一样适用。

      Detection 保持 deterministic。Band 一被突破,Claude 才被调起,tier 决定它能做什么。

      Recurring codebase scans

      Security scan 是在某个特定 model 下,关于 codebase 的 point-in-time 陈述,两半都会 stale:code 每周都在变,每个新一代 model 都比上一代找出更多漏洞。AI-Native 的答案是按 schedule 跑,——路径上无人——把发现顺着同一套 gate 送进 codebase 的其他改动走。

      Claude Security 是 hosted 形态的 schedule scanning。接一个 GitHub repo,扫描就跑在 Anthropic 基础设施上的 Claude Mythos 5,每条 finding 在报告前都被验证过,并打一个 confidence rating。Suggested patch 在 Claude Code on the web 上 review 和 apply。组织拿到拿到 finding,自己不需要有 model 访问。

      传统 · Security scanning 是一次事件,scan 在 release 前或 audit 前启动。报告送到 tracker,backlog 由人手往下处理,直到下一次事件。期间写的 code 只被 PR review 偶尔 catch 一点。

      AI-Native · 扫描按 schedule,对着每个连进来的 repo,在能力最强的 model 上跑,findings 在任何人看到前都被验证过。每条 finding 的处理方式跟被突破的 control band 一样:一个 PR 装得下的 fix 走 review gate,更大的变成 intent.md。覆盖率从最后一次 run 起算,不是从第一次。

      Prerequisites · PR review gate 与 hooks as approval gates(Stage 5: Deploy),让 findings 像其他任何改动一样被 review。Stage 1: Plan 的 intent.md 格式,留给那些"一个 PR 装不下"的 finding。

      Infrastructure · Claude Security 对 Claude Enterprise 组织 public beta 开放。它需要在目标 repo(云上 github.com)装好 Anthropic GitHub App,打开 Claude Code on the Web,开 Extra Usage 并设 spending limit,跑 scan 的人有 premium seat,以及管理员在 claude.ai/admin-settings/claude-code 打开该功能。Scan 按 Mythos 5 rate 的 consumption 计费,所以 spending limit 要跟 repo 的大小与数量匹配。

      Governance considerations · Scan 在组织 admin control 下运行——连哪些 repo、谁持有 scan seat、spend limit 都由中心设。每条 finding 都有 validation result 和 confidence rating,每个 dismissal 都有理由,所以 scan 历史就是"发现、修复、明确接受"的 audit record。

      Fix 通过 PR review gate 与 branch protection 到 production,不是由 scan 自己来。Claude Security 增强现有 static analysis 和 dependency scan。Deterministic check 留在 CI,model 驱动的 scan 覆盖那些 check 没法覆盖的、与 context 相关的漏洞。

      How to measure it · 领先:在 schedule 上的连入 repo 占比,以及从 finding 被报告到 patch 进入 PR review gate 的耗时,从 scan history 和 PR metadata 取。滞后:被 schedule scan 发现的漏洞,对照生产或外部报告发现的,从 incident tracker 取;以及经过多次 run 的 repo,每次 scan 的 finding 趋势——随着 fix 和 eval 累积,应该下降。

      Claude on call with Claude Tag

      Incident 也可以通过其他渠道进来,例如工作通讯 app(Slack、Teams)。Incident 可以是晚上 10 点在 incident channel 上的一条 Slack 消息,要求立刻修一个紧急问题——现在可以立刻动手。Claude Tag(public beta,目前 Slack 可用)让 Claude 以自己的身份成为这些 channel 的一员,每条新 incident 都有一个 first responder,response 本身也成为未来 incident 的 loop 和 memory 的一部分。

      对话和机构知识留在 channel 里,channel 里的任何人都能引导、动手 response。任何 team member 都能实时测假设、探索新选项、做调查,channel 历史也增加可审计性。通过 MCP 接入,Claude verify 指标是否回到 baseline,并在线程里确认,把 post-mortem 写进一个版本化的 lessons 文件,未来的调查可以读。

      Incident 不是 Claude Tag 唯一接的工作。在 MCP 上给 ticket 标记 tag,或在 channel 里被问到,Claude 用同样的方式 triage 这件工作。一份小、边界清楚的 fix 通过 review gate 进来变成 PR,更大的就写成 intent.md 进 Stage 1: Plan,这时 loop 开始喂自己。见:how Claude Tag runs on-call for CI/CD at Anthropic。
